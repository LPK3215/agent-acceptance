# 5 指标与目标值

> **本章角色**：[全局地图 5](00-global-map.md) 的展开正文。**P2 评测资产层收官章**——3 考卷（拿什么验）到 4 判分规则（怎么算对）到 5 **指标与目标值（多少算好）**，"考卷到裁判到分数线"三段在此闭合。
> **一句话**：查"度量基础对不对、完成率报得全不全、质量门线设在哪、SLO 五层齐不齐、成本与阶段目标有没有预算"——**本章只定义线，不执行门禁**。
> **本章边界（防越界三句）**：（1） 被评 Agent 实际跑几分是报告内容，本章判的是"**目标值设没设、口径对不对、分线合不合理**"；（2） 门禁/灰度/go-no-go 的**执行**在 8（发布流程）+ 6（观测拿数），本章提供它们的**阈值源与决策映射定义**，不重复判执行；（3） 成本**监控机制/超限降级**实现归 2.1.5 与 8 三件套，本章只判"预算上限与两段式目标线设了没"。
> **依据原则**：正文判据与阈值全部自含、可直接执行；标注"参考口径（须按场景自推）"的行业参考值不作为铁律；不依赖任何本地文件取信息，公开来源复核按名联网检索即可。
> **溯源参考（联网可检索，非本地依赖）**：本章判据由多源公开资料交叉收敛——SRE 工程实践（SLI/SLO/Error Budget，Google SRE 手册）、Anthropic《构建可信评估体系》（pass^k 客户可靠性指标）、Datawhale《动手学大模型应用开发》第十二章、酥悠沫《LLM-Agent 效果评估指南》（suyoumo.github.io：L1-L3 分层成本）、DevStudio 指标与测试策略（分域基准/生产门槛/外包验收示例）、棱镜空间三层评测金字塔（CI 门禁 pass@8≥80%/judge≥4.0/5）、公开 AgentOps 成本工程资料、行业交付验收案例（两段式阈值、完成率与步数/成本同报口径）。复核按名检索。

## 5.1 指标口径（task_success_rate 为基，禁用 http_success_rate）

**查什么**：先定"什么算一个成功"的口径——**任务级成功**而非服务级存活。接口全 200、模型输出了文本，仍可能是质量失败；用错口径，后面所有分都白打。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 5.1.1 | 度量基础任务级 | 用 **task_success_rate / golden_path_pass_rate** 作度量基础；不把 http_success_rate（接口可用性）当任务成功 | 用接口 200 / 模型有输出当作"成功"（http 200 不等于 质量成功） |
| 5.1.2 | "成功"有可判口径 | 成功判据写清：Golden 场景 pass / **有副作用任务以数据库最终状态一致性判成功**（不只看"输出了什么"） | 成功与否无定义，评审现场拍脑袋 |
| 5.1.3 | 统计性非二元 | 指标按**统计口径**设计（多次运行/样本率/记分卡），非单次二元通过不通过 | 单次跑通当通过结论（重复执行频繁失败） |
| 5.1.4 | 多面指标合看 | 不只任务成功率一项：准确率/时延/成本/失败率/满意度合看（综合记分卡） | 单指标定论（不看成本/时延/失败率） |
| 5.1.5 | 发布指标 vs 观测指标分流 | 选指标时判过"能不能影响发布动作"——**不能影响发布动作的留在观测看板，不进发布评分卡** | 发布卡堆满与决策无关的观测指标；或核心任务指标只留看板 |

**检测注意事项（5.1）**：
- 5.1.1 是最硬的口径线：凡被检方报告里只出现接口口径下的"可用性/成功率"而无任务级口径，直接判 不达标，不讨论阈值高低。
- 5.1.2 的"DB 终态判成功"只针对**有副作用/写库任务**（2.10 本体判过无写库的可跳过）；纯生成型任务以 rubric/参考答案判，不误用。
  - **出处（与 3.4 同源，两章口径须一致）**：该口径出自 **tau-bench（Shunyu Yao 等，arXiv:2406.12045，ICLR 2025）**——其评估方式即"**比较对话结束时的数据库状态与标注的目标状态**"。凡有副作用/写库任务，都应以终态比对判定，而非只看模型"说了什么"。
- 与 3.6.4 分工：3.6.4 判"评测**流程**有没有双 k 同测"，5.1-5.2 判"**指标口径**怎么定、报数怎么报"；勿重复判同一证据。

## 5.2 完成率约束（与步数/失败率/成本同报、双 k 同测）

**查什么**：完成率单报是**假指标**——一个绕 12 步、疯狂重试刷出来的 95%，输给干净利落的 92%。完成率必须与步数、工具失败率、成本**四件套同报**，且非确定性任务须双 k（pass@1 + pass@k）。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 5.2.1 | 完成率四件套同报 | 报完成率时**同时报：平均步数 / 工具失败率 / 单任务综合成本**——任一未报，该完成率"不成立" | 只报"成功率 9x%"一个数 |
| 5.2.2 | 绕远路/重试刷分现形 | 高完成率+高步数/高重试被识别为低效而非成功；**同一成功率可能代表完全不同的系统质量** | 只认成功率，疯狂重试/绕路刷分当成功 |
| 5.2.3 | 双 k 同测并声明语义 | **pass@1 与 pass@k 各报**，并写明 k 值与语义——`pass@k`=k 次至少成功一次（概率）、`pass^k`=k 次全部成功（客户可靠性）两义不混 | 只报单次 pass@1；报了 pass@k 不报 pass@1；两义混用 |
| 5.2.4 | 完成率有多次运行背书 | 完成率来自多次运行聚合（含失败 run），非"挑一次成功的截图" | 单次运行定论（非确定性未处理） |
| 5.2.5 | 效率权衡显式化 | 报告允许"部分维度变差"结论——完成率高但耗时增/成本增时如实报，而非只讲好的 | 只挑好看维度报，掩盖效率代价 |

**检测注意事项（5.2）**：
- 5.2.1 的硬承诺是**格式级**：报告模板里完成率必须自带三件套字段（平均步数/工具失败率/成本），没有字段即 不达标，跟数值高低无关。
  - **完整对照案例（三项数据缺一不可）**：两套系统 A、B——**A 完成率 95%、平均十二步、工具调用失败率 8%**；**B 完成率 92%、仅三步、工具调用失败率 2%**；结论是**综合落地价值 B 远胜 A**。
  - **引用纪律（易错点）**：此例常被简写为"95%、十二步 输给 92%、三步"，**漏掉"工具失败率 8% vs 2%"会削弱论证**——步数之外，失败率是第二个独立差距。出报告时**三项同报**。
  - **同源佐证**：另有两处独立来源支持"完成率须与过程指标同报"——Azure 把"任务导航效率"单列为独立计算器；技能类评测显示"加技能必增耗时"（即完成率提升可能伴随耗时恶化）。三处同向，此条可按"多源交叉"口径引用。
- pass@k 的 k 具体值（8 等）与 5.3 CI 门禁口径联动；语义区分（至少一次 vs 全部成功）在 3.6.4 已预警，此处判"报数是否声明了用的是哪个"。
- 成本在 5.2 是"同报项"，它的**预算线与两段式目标**归 5.5；勿在此扩写成成本章节。

## 5.3 分域目标与质量门（幻觉 / 时延 / 错误率 / 可用性）

**查什么**：质量门不是一句"90 分"，是**分域的目标值**——按任务类型定基准、按生产环境定门槛（幻觉≤5%、P95 时延、错误率、可用性），还要问一句"这线设了会不会真拦人"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 5.3.1 | 分域基准目标存在 | 按任务类型定基准/目标线（参考口径：客服 80%到目标 90% / 文档 85%到95% / 调研 75%到85% / 代码 70%到85% / 决策支持 80%到90%）——**且注明按场景自推，不照抄行业数** | 无分域，一类线打天下；或抄了行业数不推导 |
| 5.3.2 | 生产门槛有文档 | 生产门槛参考（成功率 ≥85%、幻觉率 ≤5%、时延 P95 交互 <15s、错误率 <2%、可用性 ≥99.5%）**写成文档化门槛**且标"参考口径" | 门槛只在嘴上/评审时现定 |
| 5.3.3 | 幻觉率单列口径 | 幻觉率有独立目标（≤5%，参考口径），且按 4.3 幻觉三型分型报（不单看总率） | 无幻觉率目标；或只报一个总幻觉率不分型 |
| 5.3.4 | 时延口径分交互/批处理 | 时延分场景定（参考：P50 交互 <5s、批处理 <60s；P95 交互 <15s、批 <5min；2 倍负载时延上升 <20%；恢复 <5min）——Agent 交互产品尤其要分"用户等"的交互线 | 只报服务端 P95，不区分交互/批处理 |
| 5.3.5 | 可用性/错误率有值 | 可用性 ≥99.5%、错误率 <2%（参考口径，监控窗口如 30 天/7 天写清） | 无可用性/错误率目标 |
| 5.3.6 | 质量门可执行可复算 | CI/发布层有**数值化门禁**：pass@8 ≥80%、LLM-judge 均分 ≥4.0/5（参考口径）；门槛值绑 harness 版本可复算 | 只有描述性"质量良好"，无数值、无复算 |
| 5.3.7 | 质量门三问自审 | 设门时答过三问：**在哪个环节拦（CI/发布/放量）、拦不住会怎样（进人工/回滚）、过了代表什么（不代表安全，安全另见 7）** | 门槛设了却拦不住任何人/任何流程 |

**检测注意事项（5.3）**：
- 分域目标/生产门槛数字都是**参考口径**（多为一手/二手单源），判"齐不齐"重在看有没有目标值、按没按场景推，不把具体数字当金科玉律；报告引用时标来源与可信度。
  - **来源与可信度清单（引用时照抄，防"多源交叉"名不副实）**：5.3.1 分域基准、5.3.2/5.3.5 生产门槛（成功率 ≥85% / 幻觉 ≤5% / P95 交互 <15s / 错误率 <2% / 可用性 ≥99.5%）、5.3.4 时延、5.3.6 CI 门禁（pass@8 ≥80%、judge 均分 ≥4.0/5）**主要来自 DevStudio《指标与测试策略》与棱镜空间《三层评测金字塔》两源**，属**行业整理口径（可信度：中）**——非标准、非论文、无同行评审。
  - **与 5.5.5 的关系（本章最易自相矛盾处）**：5.5.5 要求"阈值须多源交叉"，但 5.3 这批数字**实际只有上述两源，且同属行业自媒体整理，不构成真正的多源交叉**。故出报告时**不得声称这些数字已"多源交叉验证"**。
    - **正确写法**："参考口径，来源 DevStudio / 棱镜空间，可信度中，须按本项目场景自行推导"。
    - **真正达到多源交叉的只有少数几条**：（1）**双 k 同测**（Anthropic、tau-bench、棱镜空间、生产级评估白皮书均独立提出）；（2）**完成率须与步数/失败率/成本同报**（生产就绪判据、标准体系、可观测成本归因三处独立出现）；（3）**禁用 http_success_rate、以 task_success_rate 为基**（SLI-SLO 评分卡与多篇生产实践一致）。这三条可以按"多源交叉"口径引用，其余按"参考口径"引用。
- 5.3.6 的"复算"要求呼应 3.5 分数可复现：门槛本身要绑版本（改动门槛=换尺子，须记录，防"改了尺子排名就换人"）。
- 5.3 判"线设在哪、值多少"；这条线**挂没挂进 CI/发布流程**是 8 的 go/no-go，此处只查"设线时想没想过会不会真拦人"。

## 5.4 SLI-SLO 五层目标（任务成功 / 智能质量 / 工具可靠性 / 安全合规 / 可观测）

**查什么**：质量门之上，生产级项目要有**五层 SLO 结构**——从"任务成功"到"可观测"逐层设线。判齐不齐 = 五层是否都有 SLI 定义 + SLO 阈值 + 层间不互相掩盖（平均加权=红线）。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 5.4.1 | 五层 SLI 齐备 | 五层都定义典型 SLI：**任务成功**（task_success_rate/golden_path_pass_rate）、 **智能质量**（grounded_answer_rate/required_field_coverage）、 **工具可靠性**（tool_success_rate/tool_p95_latency_ms）、 **安全合规**（policy_escape_count/audit_completeness_rate）、 **可观测**（trace_completeness_rate/triage_coverage_rate） | 只定义"成功率"一层，无智能质量/安全/可观测 SLI |
| 5.4.2 | SLO 阈值按层设定 | 阈值分层写（参考口径）：任务成功 **Gold 场景 ≥99%、关键回归 100%**、智能质量 **关键字段覆盖 ≥98%**、工具 **关键工具成功率 ≥99.5%**、安全 **绕过 0、审计完整 100%**、可观测 **trace 完整 ≥99%、失败归因覆盖 ≥95%** | 无阈值或全层一个数；把 0 容忍层（安全）与可让步层（时延）混设 |
| 5.4.3 | 硬门禁与加权分离 | **硬门禁（不可妥协）**：P0 场景失败 / 安全绕过 / 审计缺失 / 跨租户数据泄露 = 一票 block；**加权（可接受风险）**：P95 延迟稍升 / 非核心少量失败 / 部分 triage 证据缺失 | 平均加权掩盖安全绕过/审计缺失（平均后看不出红线） |
| 5.4.4 | 决策映射定义 | go/no-go 决策映射写成可执行规则：**任一 hard blocker 则 block；无 blocker 且总分 ≥90 则 continue；80-90 则 canary_only；<80 则 manual_review/block** | 决策靠人临时拍；无映射规则 |
| 5.4.5 | Scorecard 契约化 | 评分卡是**机器可消费对象**：release_id / environment / window / score / decision / hard_blockers / sli 快照 / evidence / recommendation 字段齐；回答 5 问：任务成功？失败可解释？风险可接受？证据完整？发布动作？ | 评分卡是自由文本/人脑记忆，无结构契约 |
| 5.4.6 | 每日算、有 owner | 评分卡**每日计算**观察错误预算消耗趋势（非只在发布当天生成）；每个核心 SLI 映射治理 owner | 只在发布当天生成一次；指标无 owner |
| 5.4.7 | CI 接入有阶段规划 | 分三阶段演进有记录：（1）只读报告期（熟悉指标）到（2）硬门禁期（P0 Gold 失败/安全绕过/审计缺失=硬阻断）到（3）灰度策略期（延迟预算/工具正确率/trace 完整率进放量） | 一步跨到硬门禁或永远停在只读 |

**检测注意事项（5.4）**：
- "0 容忍层"与"可让步层"必须分开：安全/审计类 SLO（0、100%）不可被总分平均稀释——5.4.3 与"所有指标平均加权掩盖红线"这一反模式联动判。
- 5.4 定义目标线与决策映射；**跑分数、执行 block/canary** 是 8 发布流程动作（8.5 go/no-go 复认证），此处只查"映射定义了没、契约字段齐不齐"。
  - **5.4.2 五层阈值与 5.4.4 决策映射的出处（成套使用，禁混搭）**：均来自公开文档 **《Agent 质量 SLI-SLO 与发布评分卡》**（ai-qa-wiki，可联网检索）。五层阈值 = 任务成功 99 / 智能质量 98 / 工具 99.5 / 安全 0.100 / 可观测 99.95；决策映射 = ≥90 continue、80-90 canary_only、<80 manual_review/block。
  - **使用纪律**：这两组数字是**同一套评分卡的内部配套**，**要换就整套换**（换用另一来源的完整 SLO 体系），**不得拆开与其他来源的阈值混搭**——混搭会让"多少分给什么档"失去一致性，8.5 的 go/no-go 结论将不可解释。
- 五层 SLO 与 5.3 分域门槛的关系：5.3 是"质量门（幻觉/时延/错误/可用性）"，5.4 是**完整五层生产 SLO**，高一层；只有 5.3 无 5.4 到 判 警示（缺生产级结构），反之亦然，两层都要求文档化。

## 5.5 成本预算与两段式阈值（首月合格线 / 3 月目标线）

**查什么**：成本已是**一级验收维度**（强合规/采购场景尤甚），不是"优化项"。判三点：**有没有单任务成本预算线（多少算贵）、成本/质量/覆盖率权衡明不明示（省在哪里）、阶段目标分不分（首月合格线 vs 3 个月目标线）**——避免用终态指标卡首版，也避免成本失控上线。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 5.5.1 | 成本预算线存在 | 有**单任务成本预算/上限**（参考示例：≤0.50 美元/任务，合同示例值须自推）；成本作验收一级维度被写进验收条款 | 成本无预算无上限；报分不带成本 |
