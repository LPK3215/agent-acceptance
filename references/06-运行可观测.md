> **本章角色**：[全局地图 6](00-global-map.md) 的展开正文。**P3 运行与交付证据层第一站**——P2（3-5）把"考卷到裁判到分数线"备齐，6 起进入"真跑起来之后拿证据"：先有观测，后面 7 安全、8 上线、9 交付物全凭这里的 trace/审计数据支撑。

> **依据原则**：本章判据与量化红线全部自含于正文，不依赖任何本地文件取信息；文中出现的实证/标准名（Who&When、TraceElephant、Terminal-Bench 2.0、RewardHackingAgents、SpecBench、OTel GenAI semconv 等）均为公开来源，复核时按名联网检索即可。

## 6.1 trace/span 骨架（一次任务 = 一条 trace）

**查什么**：先看有没有**执行树结构**，而不是有没有日志。Agent 可观测的地基是：一次任务 = 一条 trace；每个 LLM 调用 / 工具调用 / 检索 = 一个 span；父子关系构成执行树；异常落在 span 状态上。没有骨架，"有日志"也看不见过程。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 6.1.1 | trace=任务 / span=调用的结构 | 一次任务 = 一条 trace；LLM 调用/工具调用/检索各为一个 span（父子关系=执行树，记录输入输出、起止时间、token、错误） | 只有平铺日志/print，无 span 结构 |
| 6.1.2 | 根 span 与关键属性 | 根 span `agent.<name>.run`，带 agent.name / session.id / 系统 prompt / 结果摘要 | 无根 span，任务与调用无归属关系 |
| 6.1.3 | 异常落 span 状态 | 工具调用/LLM 调用异常走 `record_exception` + `set_status(ERROR)`，异常落在 span 状态 | 只 console.log 错误、span 状态永远是 OK（错误靠翻日志找） |
| 6.1.4 | 遵循标准语义约定 | span 属性走**标准语义约定**，且**写明用的是哪一套**：**OTel GenAI semconv**（`gen_ai.system`、`gen_ai.operation.name`、`gen_ai.request.model`、`gen_ai.usage.input_tokens` / `output_tokens`、`gen_ai.tool.name`、`gen_ai.tool.call.arguments` / `result`）**或** **OpenInference**（`llm.model_name`、`llm.input_messages`、`tool.name`、`tool.parameters` / `output`）——采集与分析解耦、可换后端（Langfuse/Phoenix/云监控）不锁平台 | 纯自定义日志格式，无法对接任何标准后端（评估/成本报表无法复用同一份数据） |
| 6.1.5 | 跨会话/批次可观测 | 有跨会话、跨机器、可长期留存的结构化链路数据（能答三问：**一批任务整体怎样 / 成本随时间怎么分布 / 几天前那次失败能否复现**） | 只能看本机单会话实时视图；"有日志"却答不了批次问题 |
| 6.1.6 | 采集不伤体验 | 观测走异步批量采集，不阻塞 Agent 响应 | 为了埋点把交互延迟做坏 |

**检测注意事项（6.1）**：
- 6.1.4 是"可迁移性"判据：自定义格式若**能导出**为标准 OTel/OTLP 也算 达标（判出口能力，不锁内部实现），但要能喂给评测与成本报表，只进自家私有面板算 警示。
- **6.1.4 两套规范的属性名不可混写（易错点）**：**`gen_ai.*` 属于 OTel GenAI semconv**（CNCF / OpenTelemetry 官方标准，属性注册表见 `opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/`）；**`llm.*`、`tool.*` 属于 OpenInference**（Arize Phoenix 体系）。**两者前缀不同、不可混用**——把 `llm.model_name` 说成 OTel 属性名是错的，标准后端会解析不出字段。
  - **判法**：先问被检方"用的哪一套"，再看其属性名与该套是否自洽；混写（一半 `gen_ai.`、一半 `llm.`）按 警示 处理并记整改。
- 与 5.4 分工：5.4 定义可观测 SLI（trace 完整 ≥99%、归因覆盖 ≥95%），**本节判"数据骨架在不在、能不能算出那个数"**——无骨架则 5.4 的 SLI 无从计算，两章结论联动。

## 6.2 必埋字段与十字段（记录什么 = 验收项）

**查什么**：光有 span 骨架不够，要查**十字段齐不齐**。可观测的价值是"事后归因"，归因依赖快照——**缺输入与上下文快照时，≥21% 的失败无法可靠归因**（TraceElephant 实证，出处见本节注意事项），所以"记录什么"必须写成验收字段清单，而不是"有日志即可"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 6.2.1 | 必埋字段清单 | 字段写成**验收清单**而非口头约定：模型名+完整 prompt、模型返回、工具名+参数+返回值、环境状态变化、错误、重试与恢复动作、token、延迟、成本 | 只说"有日志"，列不出字段清单；缺项无感知 |
| 6.2.2 | 输入与上下文快照红线 | 每个关键 step 有**输入/上下文快照**（含 prompt 与上下文内容），支撑事后归因 | 只记输出不记输入/上下文 到 ≥21% 失败不可归因，**直接判不合格** |
| 6.2.3 | silent failure 暴露 | span 级带**质量信号**（在线 eval/judge 打分），能暴露"HTTP 200 但质量退化" | 只有时延/错误率/状态码，看不出"答得对不对" |
| 6.2.4 | 快照脱敏 | 上下文快照含敏感信息时有脱敏/不落明文机制（与 2.2.6 联动）；记录 不等于 裸存 | 快照原样含密钥/个人信息落明文存储 |
| 6.2.5 | 推理过程留存 | span 记录"推理了什么"而不只"调了什么"——模型返回含 reasoning 时留存，供回放与质量诊断 | 只记 API 元数据不记推理/返回内容 |
| 6.2.6 | 异步采集 + 数据完整一致 | 异步批量采集保证时间区间完整、父子关系明确（执行层级由模型运行时决定、深度不固定时仍能还原调用树） | 采集丢失 span / 时间区间断裂 |

**检测注意事项（6.2）**：
- 6.2.2 是**格式级红线**（与 5.2.1 同级）：快照字段缺失即判 不达标，不是讨论"要不要埋"。
  - **"≥21% 不可归因"的出处（易错点，与 4.6.5 口径须一致）**：该值出自 **TraceElephant（arXiv:2604.22708，ACL 2026）**——作者分析 **Who&When 的 184 个失败案例**，发现**至少 21% 在 output-only（仅输出日志）条件下无法可靠归因**。
  - **引用纪律**：这是 **TraceElephant 对 Who&When 数据所做的分析**，**不是 Who&When 论文本身的结论**。写作时表述为"TraceElephant 分析 Who&When 的 184 例失败得出上述发现"，**不得写成"Who&When 实测/指出"**。
- 判"快照"时注意区分两义：**记录输出**（多数系统都有）vs **记录输入+上下文**（决定归因上限的字段）——只记前者按缺 6.2.2 处理。
- 6.2.4 与 7 数据治理衔接：本处只判"快照有脱敏机制"，留什么/删什么归 2.10.4/7.6。

## 6.3 归因粒度与失败定位（step 级归因供得起吗）

**查什么**：失败之后能不能说清"错在第几步、为什么"——**step 级归因是硬指标**（agent 级 65.9% vs step 级 30.3%，全可观测轨迹下才到这水平；只看输出 ≥21% 不可归因）。6.3 只判观测侧**供不供得起**这个能力。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 6.3.1 | step 级归因数据支撑 | 观测数据能把失败定位到**第几步**（每 step 的输入/输出/工具调用/环境态可查） | 只能说是"哪个子 agent 的锅"（agent 级），定位不到 step |
| 6.3.2 | 可复现环境配套 | step 级归因**配可复现环境**（失败样本可重放复现，+10% 归因增益） | 只给"第 N 步错了"一句话，无法复现验证 |
| 6.3.3 | 归因覆盖诚实上报 | 缺输入/上下文快照导致的不可归因比例**如实报**（trace 完整率/归因覆盖率作为 SLI 在 5.4 口径内可算） | 掩盖不可归因部分，只报能归因的样本 |
| 6.3.4 | 失败有追溯闭环 | 失败 trace 能进入**失败样本回流**（回放 到 归因 到 修复 到 重跑验证），不是查完即弃 | trace 只有展示用途，失败不留痕不回流 |
| 6.3.5 | 动态深度完整还原 | Agent 执行层级由模型运行时决定、深度不固定时，链路仍能还原完整调用树（父子明确、区间完整） | 动态嵌套场景丢 span/无法重建层级 |

**检测注意事项（6.3）**：
- 与 4.6.5 分工（重审勿重复判）：4.6.5 判**判分器报告**是否声明归因粒度（agent 级 vs step 级、把 agent 级当 step 级=不达标）；6.3 判**观测层字段**能否支撑 step 级归因与复现。两者证据不同：4.6.5 看报告文本，6.3 看 trace 数据本身。
- 6.3.1/6.3.2 的经验值（65.9/30.3/+10%）来自 TraceElephant 公开研究（全可观测轨迹 agent 级 vs step 级归因对比），是参考实证，判"支撑能力在不在"，不拿这两数当达标线。
- "错在第几步"须以**有快照的 step**为凭（呼应 6.2.2），无快照的归因断言按未证实降级（9.2）。

## 6.4 审计日志与链路回放（可追溯 + 可回放）

**查什么**：过程记录不只是给开发者调 bug，还是**验收证据**。查两点：（1）**结构化审计日志**（事件可导出、可检索、构成交付物）；（2）**链路回放**（几天前的一次失败能不能重放出来）。trace 可回放已是验收硬项。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 6.4.1 | 结构化审计日志 | 有结构化审计日志（事件流落盘：谁/何时/做了什么/结果，可导出可检索），是交付物 10 项之一（9.1 复核） | 只有自由文本日志，无事件级审计记录 |
| 6.4.2 | 链路回放能力 | 一次失败可**重放复现**：Thought/Action/Observation 结构化落盘可回放可对比；会话事件流跨会话留存（能复现"几天前那次失败"） | 日志看完就没了；单会话实时视图不能跨会话复现 |
| 6.4.3 | 成本/延迟可归因 | trace 带 token/延迟/成本，能按 **agent/用户/任务维度**拆分（成本归因），供 5.5 预算复核与 ROI | 成本只有总账单，无法归因到具体 agent/任务 |
| 6.4.4 | 行为可追溯 | 审计记录支撑"行为可追溯"（做了什么、能否重演），日志可导出（呼应 7 安全三问与国标行为主轴） | 审计内容不可导出/丢失/只有内存态 |
| 6.4.5 | 回放是验收硬项 | "trace 可回放"作为验收项存在（不是可选优化）——token/延迟/回放能力已指标化 | trace 回放被当"锦上添花" |
| 6.4.6 | 审计与观测分流 | 审计日志（合规证据）与调试 trace（工程诊断）职责分得清——审计子集可独立导出、不被调试噪声淹没 | 两者混在一份日志里互相污染 |

**检测注意事项（6.4）**：
- 审计的**合规对照**（保留期/防篡改/政策）不是本节点——7/2.10.4/9.5 判；6.4 只确认"审计日志在不在、结构化、可导出、可回放"。
- 6.4.2 的"可回放"判据是**能重放复现一次历史失败**（拿 trace 数据 + 版本把当时场景跑回来），不是"回放 UI 有播放键"。UI 有回放但数据不完整=警示（够展示不够复现）。

## 6.5 版本绑定与奖励黑客插桩（分数不乱码、防钻评测空子）

**查什么**：观测数据若不带版本，回放就失去参照系——**分数必须绑定 harness 版本号**（同模型换 harness 波动 10-20 点是常态，极端可达数倍，实证见本节注意事项）。同时要防"agent 为过评测而钻空子"——**奖励黑客插桩**是观测侧防线。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 6.5.1 | 分数绑定 harness 版本 | trace/评测分数带 **harness 版本号**；版本变更（改 harness/换实现）即失效原分数，不横向挪用 | 只报分数不带版本；拿"同模型不同实现"的分数互比 |
| 6.5.2 | 发布对象与运行版本绑定 | 回放能定位到"哪个发布对象 + 哪个运行版本"（与 2.11.4 版本化运行联动）；换版本后历史 trace 仍可对照 | 回放时不知道当时跑的是哪个版本 |
| 6.5.3 | 奖励黑客插桩 | 观测/评测侧有**插桩**：per-episode 工作区快照 + 补丁追踪 + 文件访问插桩 + 可信参考指标 + 显式信任制度，能分离"eval hacking"与真实能力 | 无任何插桩——agent 改文件/利用漏洞过评测无法被发现 |
| 6.5.4 | 按任务长度分层统计 | 评测分数**按任务长度分层**报（长任务 hacking 恶化——SpecBench：随任务变长 hacking 会恶化，评测要配套） | 不分层，长任务钻空子被短任务均值掩盖 |
| 6.5.5 | 插桩不伤真跑 | 观测/插桩本身不影响被测行为（无观测者效应）；插桩层与业务层解耦可开关 | 插桩改变 Agent 行为/性能，测的不是真实运行 |
| 6.5.6 | 打分基准显式可信 | 有"可信参考指标"锚定（防 agent 只优化可 hack 的 proxy）；评测完整性当可测对象而非默认成立 | 只信自报分数，无防 hack 参照 |

**检测注意事项（6.5）**：
- 与 3.5 分工：3.5 判**数据集/评分器侧**污染与可复现性；6.5 判**运行观测侧**的 harness 版本绑定与奖励黑客插桩——两个防作弊面，勿以一面代两面。
- **"换 harness 即换分数"的实证（已回源，可直接引）**：
  - **Meta-Harness**（斯坦福 IRIS Lab，Yoonho Lee 等，2026-03）：在 **Terminal-Bench 2.0** 上，同一模型 **Claude Haiku 4.5** 换不同 harness 得 **Terminus-KIRA 33.7% / Goose 35.5% / Meta-Harness 优化后 37.6%**——模型、工具环境、评测协议全不变，只换 harness 分数就不同；该文另有小模型 harness 追平大模型的结果。
  - 同类工作（上海 AI Lab，2026-07）在 Terminal-Bench 2.0 上报告：**底层模型、工具环境与评测协议保持不变、只改 harness，提升可达 104%**——即分数可被"换壳"翻倍，远超"10-20 点"的常规幅度。
  - **参照锚点**：Claude Opus 4.6 在 Terminal-Bench 2.0（89 题基准）官方榜单为 **65.8%**。引用任何 Agent 分数时，都必须连带说明"哪个 harness、哪个版本"。
  - **引用纪律（易错点）**：曾见公开行业技术转述称"Claude Opus 4.6 从 58% 到 76%"（连同"Gemini 3 Pro 56% 到 69%"）——属**二手行业转述**，无官方/一手链路，且与官方榜单 65.8% 口径的**对应关系不明**（官方 65.8% 可能是官方 harness 下的成绩，两数未必矛盾）。
    - **处理**：**不得升格为判据引用**（单源、口径不明），但**也不可写"经核为假/查无此文"**——查无此文属不实。需引用时表述为"行业技术转述存在 58% 到 76% 量级的 harness 差异"，判据论证用上列三条可核事实即可，结论只更强不更弱。
- 奖励黑客插桩在纯 demo/未上生产场景可不全配（per-episode 快照等成本高），判"有没有对应机制或显式豁免说明"；生产/强合规场景（5.5 升档）则按 不达标 处理缺项。
- 6.5.3/6.5.4 呼应附录 A.2 反模式"分数能不能信 到 奖励黑客插桩已做"作为背书；缺插桩时自报分数按未证实降级（9.2）。

## 本章收口：运行可观测判定与后续分诊

6 跑完，输出**可观测判定表**：

1. **逐节结论**：6.1-6.5 每节 = 达标/警示/不达标，附缺项清单（骨架/字段/归因/审计/版本绑定各缺什么）。
2. **数据红线**：缺输入与上下文快照（6.2.2）到 直接不合格；仅此一项会连锁拖垮 6.3（归因供不起）与 6.4（回放不完整），报告按"该层观测不可用"处理。
3. **版本绑定硬承诺**：凡报分数/回放，必须能对上 harness/运行版本号（6.5.1/6.5.2）；无版本可绑的观测数据不可作证据（9.2 未证实降级）。
