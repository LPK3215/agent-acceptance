# 2 本体构成

> **本章角色**：[全局地图 2](00-global-map.md) 的展开正文。**P1 本体可查层**——"被检方提供物 = 源码 + 文档即可查"，无需先交评测资产。
> **一句话**：把 Agent 拆成本体全景母图（认知核心+主体部件+资源供给）逐块查"齐不齐、接没接线"——本章只判**本体有没有、是不是真实可用**；量化做得"够不够好"归 3-5，安全/权限深检归 7，运行交付归 8。
> **使用方式**：逐条过检查点——（1） 达标/不达标/警示 （2） 证据（源码文件/配置/文档/命令输出） （3） 不达标/警示 落整改建议。判点是**代码层判定**：问"这部件是否存在、是否真接线"，不臆断其内部实现优劣。
> **依据原则**：正文判据自含、可直接执行；涉及的公开工程实践/基准（Datawhale 智能体课程、GAIA、ToolFailBench、awesome-agentic-ai-zh 课程、LangChain、durable checkpoint 工程实践等）均按名可联网检索复核，不依赖任何本地文件取信息；表内"x.y"为区内章节文字引用。

## 2.1 模型与认知核心层（Model Management）

**查什么**：认知核心 = 用什么模型、怎么管版本与参数、换模型护栏怎么护、成本配额有没有闸。这是五特征最底层，缺它后面全是空转。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.1.1 | 模型选型与供应商 | 能说出哪家/哪个版本/为什么（按任务类型、成本、延迟选型，有对比记录或理由）；有统一模型网关概念 | "用了大模型"答不出版本与选型理由 |
| 2.1.2 | 模型版本管理 | 记录模型/Prompt 版本；升级可回滚；变更前有评估 | 版本无记录，升级即不可逆 |
| 2.1.3 | 推理参数固化 | temperature/retry_limit/fallback 等**显式配置**（如 `temperature:0.1`+`retry_limit:3`+`fallback:human_audit`），随机性与失败处理可复现 | 无显式随机性/重试/兜底配置——每次跑分可能不同，无确定性评估前提 |
| 2.1.4 | 换模型的护栏影响 | 升级/换模型前全链路复测；移除某条 harness 补丁有同组 Eval 证明；**权限/安全/log/eval/recovery 不因模型变强自动过时** | 直接换新模型并顺手拆护栏（"模型变强了就不用那层防护了"） |
| 2.1.5 | 模型调用成本与配额 | 有成本账本指标；设每日上限/超限行为（停止/降级/排队）；有预算告警 | 循环执行无花费上限、费用异常后才补 |

**检测注意事项（2.1）**：
- 判"达标"要看**源码/配置里的显式参数**，不是听被检方说"我们设了低温度"；证据=配置文件行、环境变量、网关路由表。
- 模型选型不锁具体厂商版本——规范断言"有据可查的选择+可回滚"，不替项目定型号。
- 若项目换模型是常态（多模型路由），2.1.4 必查：每次切换都要走"换护栏到复测"流程，不能只换不改护栏。
- 选型实证口径（参考，非达标线）：**同任务不同"接入形态"差异极大——纯浏览器 14.9% / 纯 API 32.1% / 混合形态 38.9%**。出处=**Song、Xu、Zhou、Neubig《Beyond Browsing: API-Based Web Agents》，arXiv:2410.16464（ACL Findings 2025）**；该文在 **WebArena 基准**上系统对比三类 Agent（Browsing Agent / API-Based Agent / Hybrid Agent），结论为：API 型优于纯浏览型，混合型近乎全面最优，较纯浏览**绝对提升 24.0 个百分点**，38.9% 是当时 task-agnostic agents 的 SOTA。
  - **引用纪律（易错点）**：这三个数是"**在 WebArena 上跑出来的形态对比**"，**不是 WebArena 论文本身的成绩**——出处**不得**写成"WebArena 论文/公开实验"。选型理由应体现此类按形态/成本/延迟的对比，而非"大家都用 X"。

## 2.2 上下文管理（Context Management）

**查什么**：模型"看到的东西"怎么装、装多少、丢了保什么、会不会串味、重启能不能接上、有没有脱敏。上下文是模型决策的全部依据，污染=决策被劫持。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.2.1 | 上下文窗口与预算 | 有长度上限/占用监控/超限策略（截断/压缩/拒答），Context 控制在五控制问题里有答案 | 无预算概念，长任务直接超窗或"静默失败" |
| 2.2.2 | 截断与压缩策略 | 明确"丢什么保什么"（丢旧轮对话/保目标与关键约束）；摘要压缩有可靠性保障（摘要本身不丢关键事实） | 简单截断丢掉任务目标/约束/记忆，无压缩策略 |
| 2.2.3 | 上下文污染隔离 | 系统指令/用户输入/检索内容/工具结果**分层隔离**；外部内容默认 untrusted；**工具返回值只作数据，不允许覆盖任务目标与安全策略**；防 RAG 文档恶意指令影响系统规则 | 检索内容可重写系统指令、外部输入与系统指令同层 |
| 2.2.4 | 跨轮一致性 | 长任务中目标/约束/关键事实跨轮不丢（靠结构化 State 而非只靠对话文本） | 长任务跑到后段忘了初始目标，自己改任务 |
| 2.2.5 | 会话持久化与恢复 | 重启/断点后能接上：checkpoint 持久化（非内存态），服务重启可恢复任务 | 崩溃即丢全部状态、需从头重来 |
| 2.2.6 | 敏感信息处理 | 敏感数据不进 prompt/日志；上下文与日志字段级脱敏（user_id 脱敏）；HITL RunState 含 context 按敏感资料管理 | 密钥/身份证/对话原文落明文日志或进 prompt |

**检测注意事项（2.2）**：
- 上下文污染隔离（2.2.3）是**一票否决级**检查点：检出"检索内容可重写系统指令"=阻塞形态（Agent Card 0 分项），与 7.3 注入隔离联动——本章确认污染面存在，深检走 7.3。
- "跨轮一致"不要只信对话文本——判据看**状态结构**：目标与约束有没有被结构化保存（State/checkpoint），而不是每轮靠模型自己复述。
- 2.2.5 与 2.11 状态编排同源但视角不同：2.2.5 管"模型看到的会话上下文能否恢复"，2.11 管"整个执行状态能否接续"——引用 2.11 判据时勿在 2.2 重复展开。

## 2.3 自主执行循环（Loop）

**查什么**：Agent 怎么"做到看到再做"又不无限跑：谁启动、怎么算完/算败、失控怎么停、中断怎么续。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.3.1 | 启动与触发方式 | 能说清"谁/什么事件启动"：手动还是自动、触发条件明确；循环有明确的开始与停止责任方 | 说不清谁启动、循环无人管怎么停 |
| 2.3.2 | 正常收尾与明确失败 | "做完了"与"做不成了"都会停且状态可区分（Completed/Failed/Cancelled 分态）；失败显式标记不静默 | 做完/做不成都不报，状态只有"跑了"；context 超限时静默无报错 |
| 2.3.3 | 死循环与失控防护 | 有步骤上限/超时/自锁：loop 有轮次上限、超时即止、到达上限明确收尾（非继续烧 token） | 无轮次上限/无超时，可能无限跑烧钱 |
| 2.3.4 | 中断恢复与断点续跑 | 暂停后能从断点继续而非从头重来；恢复点=结构化 checkpoint | 中断只能重跑全程 |

**检测注意事项（2.3）**：
- 三种 Loop 必须分开查：**程序循环**（同一段代码）不等于 **Agent Loop**（模型到工具到结果到模型，一次 run 到完成或 max_turns）不等于 **Loop Engineering**（跨 session 反复，每轮问"目标还成立？继续/停止/交给人"）。2.3 查的是 Agent Loop 本体；跨 session 的停止/升级决策属 Loop Engineering，在 2.4/7.4/8 联动。
- 死循环防护判据要看**代码里真实的上限与终止分支**，不能只看"有 max_turns 常量"——要确认到达上限后确实停止并落失败状态（对应 2.3.2）。
- 本项目若含"长任务自动续跑/定时触发"，需同时确认 2.3.1 触发条件不依赖人肉盯着，且与 8 超时即止口径一致。

## 2.4 规划与推理落地（Planning & Reasoning）

**查什么**：Agent 会不会把任务拆成可执行步骤、按计划走、动态调整、长任务不丢目标——这是"自主性"区别于"一次问答"的分水岭。本体层只查"有没有落地执行且可查"，好坏量化归 3-5。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.4.1 | 任务分解成可执行步骤 | 任务被拆成步骤且每步可执行可验证（有中间产物/checkpoint 语义） | "拆了"但拆出的是空话步骤，无法执行/验证 |
| 2.4.2 | 链式推理可追溯 | 每一步推理/决策有 trace 记录（想了什么、调了什么、基于什么）；从结果能回查推理链 | 只能看到最终输出，中间推理不可查 |
| 2.4.3 | 计划与实际执行推进 | 计划到执行之间有真实推进（做了能看结果再决定下一步），不是一步到位碰运气 | 计划与实际执行脱节，编个计划但实际乱走 |
| 2.4.4 | 动态调整与失败处理 | 执行遇阻能重规划/换路径（失败到分析到改计划到再试），有调整上限防死循环 | 遇阻直接卡死或无限重试同一路径 |
| 2.4.5 | 长任务目标保持 | 长任务执行中初始目标/关键约束不丢（Plan 在 State 里不被覆盖）；几十步任务能回到目标 | 执行中自行改目标/忘约束，与 2.2.4 跨轮一致性联动 |

**检测注意事项（2.4）**：
- 本体层查"规划**存在且接线**"：能指认规划模块/中间 Plan 状态/调整逻辑在哪；量化好坏（规划质量打分）归 3-5，本章不越界判好坏。
- 判断"真调整还是假调整"：看 trace 里失败后是否**换了策略/工具/子目标**，而非同路径无限重试（后者属 2.3.3 死循环）。
- 若项目声明"无显式规划"（简单工具人形态）：需说明靠什么保证多步不跑偏（如直接任务+强验证），不能用"没规划"回避 2.4 检查——对应 1 自主度 G 档归档后按档位简化。

## 2.5 工具与技能接入层（Tool & Skills）

**查什么**：Agent 能调用什么工具/技能、注册是否规范、参数传得对不对、结果消化了没、调得实不诚实、失败降级怎么处理。**工具描述不准确是多数工具选错之源**，直接决定能不能干成事。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.5.1 | 技能管理与注册 | 技能=指令文档+工具/资源打包，有清单/注册表；技能可发现（名字/描述/入口清晰）；按需加载 | 技能散落无清单，同名冲突，无法发现 |
| 2.5.2 | 工具 schema 与描述质量 | 每个工具 schema 完整、描述准确、参数说明到位、由谁注册有流程 | 描述含糊导致模型选错工具；schema 与实现不一致 |
| 2.5.3 | 调用参数正确性 | 工具调用的参数按 schema 正确传递；等价调用可判定（名字精确/键值集合等价/值语义等价） | 参数类型错、必填漏、键名不一致；把 A 工具参数传给 B |
| 2.5.4 | 调用诚实性 | 真实调用了声明的工具；不虚构成功（失败会说失败）；不做无实际作用的多余调用 | 声称"已调用/已成功"但实际未调；虚构执行结果 |
| 2.5.5 | 结果消化与使用 | 工具返回值真的被下一步使用（不是调了白调）；对返回状态有判断（成功/失败/异常分得清） | 调了工具但结果不进入推理；把失败当成功继续 |
| 2.5.6 | 失败重试与降级 | 工具失败有 retry/降级/兜底路径（不是无限重试）；错误状态清晰可观测 | 工具失败即崩/静默/无限重试 |
| 2.5.7 | 业务系统接口接入 | 能枚举至少一类真实接入通道（HTTP API / OpenAPI / 数据库接口 / MCP 服务 / 内部能力包）；通道有凭证、超时与鉴权管理；声称接入的系统有真实调用证据（非 mock/演示桩） | 只具备问答能力、无任何业务系统接入（进不了生产流程）；或"已接入"仅演示桩、无真实通道 |

**检测注意事项（2.5）**：
- 参数正确性判据有客观方法：**AST 匹配三规则**（Datawhale《第十二章 智能体性能评估》第 12.2 节，源自 **BFCL**（UC Berkeley）的判法口径；GitHub: `datawhalechina/hello-agents`）可直接做成脚本化检查——抽样 N 次工具调用，逐条判：（1）**函数名精确匹配**（`get_weather` 不等于 `get_temperature`）；（2）**参数键值对集合相等、忽略顺序**（`f(a=1,b=2)` 与 `f(b=2,a=1)` 等价）；（3）**参数值语义等价**（`x=2+3` 与 `x=5` 等价；单双引号字符串等价）。
  - **多函数调用的补充规则（脚本化时必须带上，漏了会大量误判）**：要求调用**数量相同**、每个调用都匹配，但**调用顺序可以不同**（集合匹配）。
  - **判法纪律**：工具调用正确性**不能按整串文本比对**来判，必须按"名字 + 参数集合 + 语义等价值"判；且**分难度/分类别单报**，不混成一个总数。BFCL 的 simple / multiple / parallel / **irrelevance** 四类中，**irrelevance 专门考"该不该调用"**——不需调用时必须不调用，这一类是 2.5.6"多余调用"的现成题型来源。
- 本章只查"接入层本体质量"；**权限/鉴权/最小权限/敏感工具锁定归 7.2**——勿在 2.5 重复 7 判据。
- 2.5.7（业务系统接口接入）与 2.10.1 分工：2.10.1 判"数据读写分层与 schema 校验（防脏数据/直连乱写）"；2.5.7 判"业务系统接入**通道种类与真实性**（能不能真连生产系统、接的是哪类接口）"——对应五能之"接入业务系统"一项的落点。通道变更的版本化与回滚归 8.4.1。
- 工具失败四分类可当 2.5.4/2.5.5 的子项验收清单。出处=**《ToolFailBench: Diagnosing Tool-Use Failures in LLM Agents》，arXiv:2607.04686（ICML 2026）**；四类为 **Tool-Skip（该调没调）/ Result-Ignore（调了不用）/ Output-Fabrication（编造返回值）/ Unnecessary-Tool-Use（多余调用）**，基准规模 1000 条工具使用任务，横跨金融、医疗、法律、网络安全等领域。
  - **判据化用法（硬要求）**：四类须**分别计数，不得只报一个总成功率**——"该调没调"与"编造返回值"会互相掩盖，总成功率看不出问题。与 4.3 匹配与判定算法联动使用。

## 2.6 记忆机制实现（Memory）

**查什么**：短期（会话内）/长期（跨会话）记忆有没有、记忆存取是否准确、防不防注入污染、能不能查改删、有没有参与决策。**没有记忆评测的记忆，可能"记住却记错"**。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.6.1 | 短期记忆（会话内） | 会话内关键信息能跨轮保持不丢（上下文机制+结构化）；不靠超长原文硬扛 | 每轮失忆/靠重复塞全文 |
| 2.6.2 | 长期记忆（跨会话） | 有跨会话记忆存储；存取有明确读写边界（谁可写/何时写/何时读） | 无长期记忆；或所有信息无差别长期堆积 |
| 2.6.3 | 记忆准确性与防污染 | 检索出的记忆能被验证为"真实发生过"；防止 prompt 注入/对话内容把假信息写进长期记忆；恶意指令不能污染记忆库 | 对话中恶意内容被当成事实存入记忆并永久生效 |
| 2.6.4 | 记忆可管理性 | 记忆可查看/修改/删除/过期；用户能纠正或清除错误记忆；有记忆隔离（不串用户） | 记忆黑盒不可查不可删，用户无法纠正错误记忆 |
| 2.6.5 | 记忆参与决策的可观测 | 能从 trace 看出"这次回答用了哪条记忆"；记忆影响结果可追溯 | 无法判断回答来自记忆还是编造 |

**检测注意事项（2.6）**：
- 2.6.3 是**安全联动点**：记忆污染 = 7.3 注入的攻击面延伸。本体层确认"有没有防污染写入口"，攻击深度测走 7.3。
- 记忆正确性判断需测评：长期记忆评测（**MemoryAgentBench 四能力=accurate retrieval 准确检索 / test-time learning 测试时学习 / long-range understanding 长范围理解 / selective forgetting 选择性遗忘**，见 Hu、Wang、McAuley《Evaluating Memory in LLM Agents via Incremental Multi-Turn Interactions》，**arXiv:2507.05257，ICLR 2026**）是乙类证据，归 3-5 量层，本章只确认"存在+接线+可管理"。
  - **防误**：第四项原文为 **selective forgetting（选择性遗忘）**；部分中文二手解读写作"冲突解决"，**引用一律以 arXiv 原文为准**。
  - **可直接借用的结论**：该文实测"现有方法无一同时掌握四项能力"（含长上下文、RAG、外部记忆模块、带工具的高级 Agent）。故**记忆能力声明须逐项举证，不接受一个总分背书**——被检方若声称"记忆很强"，要求其分别给出四项上的证据。
  - **同类记忆题源（参考口径，单源待回源）**：LoCoMo（100+ 轮长对话、关键信息在 10/30/60/90 轮埋入再测回忆）可作"长程回忆衰减"的现成测法；判"测过记忆"看有没有这类**随时间埋点、跨很多轮才回收**的用例，而非只测同会话内回想。
- 记忆隔离（2.6.4）多租户深检归 7 数据隔离，本体层记"是否隔离串味"即可。

## 2.7 反思与自我改进回路（Reflection）

**查什么**：Agent 会不会在失败/不确定时复盘、定位错因、修正再试、并把经验沉淀下来——这是它区别于"重复犯错工具"的成长性。本体层查回路存在与接线，成长幅度量化归 3-5。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.7.1 | 反思触发机制 | 失败/异常/不确定时能触发复盘；有明确触发条件（非每次无脑重试） | 从不复盘，失败只会原样重试 |
| 2.7.2 | 反思质量与归因 | 能定位"哪一环错"（检索/模型/工具/规划/状态），不是笼统"我错了" | 反思空泛，无法指出具体失败环节 |
| 2.7.3 | 修正闭环 | 反思确实改变下一次动作（换工具/改 prompt/调计划/补资料），有再验证 | 反思了但行为不变，复盘=形式主义 |
| 2.7.4 | 经验沉淀 | 教训沉淀为可复用物（回归用例/文档/技能修正/记忆纠错），下次可避免同类错误 | 教训只存在本次对话里，重启即忘 |

**检测注意事项（2.7）**：
- 反思回路好坏是动态量，本体层只确认"触发点存在 + 归因逻辑 + 行为可变 + 沉淀落点"四环齐不齐；闭环幅度用 Reflection Score 等乙类指标在 3-5 量。
- 注意区分：2.7 查"系统有没有自动反思回路"；若项目把反思放在人审（人工 review 后改），属 HITL 反馈，归 7.4/8 人审机制查，不硬套自动反思判据。
- 经验沉淀（2.7.4）与 6 回归套件联动：事故到用例的落点应在可执行回归里，不是只写"下次注意"。

## 2.8 知识库与 RAG（Knowledge & RAG）

**查什么**：给 Agent 喂知识的整条链路：文档来源到解析到切片到向量化到检索到引用到权限过滤到更新维护。RAG 质量决定"答得准不准/敢不敢说不知道"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.8.1 | 文档来源与入库 | 知识来源明确可溯源（文档/链接有出处记录）；入库有流程（谁提供/何时入库/版本管理） | 知识来源不明，无法追溯是谁的知识 |
| 2.8.2 | 检索链路完整 | 解析到切片到向量化到检索到（重排）链路真实存在且可观测；切片有 metadata | 只有"向量库+相似度"无全链路；或切片无元信息 |
| 2.8.3 | 引用溯源 | 回答能定位到具体文档/页面/切片（引用出处）；可验证"不是编的" | 答得看似专业但无出处，无法核对 |
| 2.8.4 | 知识更新与失效处理 | 有更新机制与版本；知识过期/删除后能同步；未收录/不确定时不硬答（可拒答或转人工） | 知识库永不更新；问未收录知识硬编答案 |
| 2.8.5 | 权限与访问边界 | 检索时按权限过滤（租户/角色/密级）；不同用户检索范围不同；敏感文档不进无权者的上下文 | 全库一把梭检索，权限过滤缺失 |

**检测注意事项（2.8）**：
- RAG 检索质量好坏 = 乙类评测（RAGAS/准确率等）归 3-5；本章查"链路完整性+引用性+更新性+权限性"四性是否存在。
- 引用溯源（2.8.3）与"诚实性/不确定拒答"（2.8.4）强联动：能拒答未知是成熟标志，别把"答不出"全当缺陷。
- RAG 对抗攻击（提示注入藏文档、权限绕过）深检归 7.3 注入隔离与 7 权限；本章确认"权限过滤在检索层生效"即可。

## 2.9 文档与内容解析（Document Parsing）

**查什么**：喂给知识库/上下文的内容解析质量：格式覆盖、解析正确性、低质量输入处理、解析管线可观测。这是 RAG 链路的输入端，解析错则全链路错。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.9.1 | 支持格式与来源覆盖 | 项目所需文档格式（PDF/Word/网页/图片等）有解析路径；声称支持的格式真能解析 | 只支持演示格式，真实业务格式解析不了 |
| 2.9.2 | 解析正确性 | 表格/图片/复杂版式/公式解析不乱；解析结果有人抽查校验；解析错误能定位到文件与环节 | 解析出来乱码/丢表/错位而无校验机制 |
| 2.9.3 | 低质量源处理 | 扫描件/模糊图/坏文件能识别并处理（OCR 失败/质量差到标记或拒收，不硬编） | 质量差内容被静默解析成错误文本进知识库 |
| 2.9.4 | 解析管线可观测 | 解析耗时/失败率/错误可观测可追踪；新格式接入有流程 | 解析黑盒，失败无日志，出了问题不知哪一环 |

**检测注意事项（2.9）**：
- 解析正确性本体层用**抽样法**：从真实输入取 N 份文档人工核对解析结果（表格结构/OCR 文本/版面顺序），记录错漏率；做得好不好量化归 3-5。
- 若项目不做知识库（无文档输入）：2.9 整节可标注"不适用（无文档型输入）"并说明依据，勿硬查。
- 解析是注入入口之一：恶意构造文档（含指令的 PDF/表格）解析后可能带注入 payload，深检归 7.3。

## 2.10 数据与文件管理（Data & Files）

**查什么**：Agent 读写数据/文件的机制质量：存取设计、一致性、权限、生命周期、文件组织。本体层查"会不会把数据搞坏/搞乱/搞丢"，安全细项归 7 数据隔离。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.10.1 | 数据读写接口与设计 | DB/API/文件读写有明确分层与接口；schema 有校验（读前校验模式）；防脏数据注入 | 到处直连数据、无 schema 校验、格式靠猜 |
| 2.10.2 | 写入一致性与幂等 | 关键写操作幂等或事务化（重试不会双写）；写失败有明确状态 | 重试导致重复下单/重复写入无幂等保护 |
| 2.10.3 | 文件权限与路径安全 | 文件/路径访问按最小权限；防路径穿越/越权读文件；用户文件与系统文件隔离 | 任意路径读写、无权限边界、路径可注入 |
| 2.10.4 | 数据生命周期 | 临时文件/缓存有清理；数据有保留与过期策略；删除可执行（用户要求删除能真删） | 临时数据堆积不清理；删不掉/删不干净 |
| 2.10.5 | 文件组织与可维护 | 文件目录结构清晰、命名一致、版本管理在（不覆盖用户文件） | 文件散落无结构、随意覆盖已有文件 |

**检测注意事项（2.10）**：
- 幂等性是本章最硬判据之一：**对"会写外部系统"的工具，必须检查重试是否安全**（是否带幂等键/事务/状态检查）——重试双写是真实生产事故级缺陷。
- 数据隔离/敏感数据/租户边界不在此章深挖，指向 7.2（权限）与 7.6/2.6.4（数据与记忆治理）。
- Agent 若写文件/改文件，必须有"不覆盖用户数据"保护，这是与纯聊天工具的本质差异点。

## 2.11 状态编排与 Orchestration（State & Orchestration）

**查什么**：多步执行的编排结构：状态怎么存、恢复怎么接、编排逻辑可不可见可控、是否 durable。它是长任务与自动化的地基。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.11.1 | 状态持久化（durable） | 执行状态存**持久化存储**（DB/checkpoint），非仅内存；崩溃后状态还在 | 状态只存在内存/进程里，重启全丢 |
| 2.11.2 | 断点续跑与恢复 | 任务能从中断点恢复；状态恢复后上下文/进度一致 | 恢复后状态错乱或只能从头跑 |
| 2.11.3 | 编排结构可控可观测 | 执行图/步骤流可查看（当前在哪步/历史步骤/可干预）；分支可理解（不是一团黑盒循环） | 编排黑盒不可观察，出事无法定位 |
| 2.11.4 | 状态与版本管理 | 状态/流程变更可回溯；发布新逻辑不影响在跑任务或能平滑迁移 | 状态结构变更即历史任务全废 |

**检测注意事项（2.11）**：
- 关键区分：**内存态 = 演示级**；**持久化 checkpointer = 生产级**。看到编排框架自带的 in-memory store 别放行，要确认 state 落到持久层（数据库/磁盘）再判 达标（durable checkpoint 是生产硬要求，公开工程实践可按名检索）。
- 编排层与执行层解耦与否：若 Agent 逻辑写死在编排节点里无法单独重启/替换某步，恢复能力必然弱。
- 地图 2.11 标"状态编排/Harness 运行时"双归属：本章 2.11 查"状态与编排"，Harness 运行时装进 2.12 合并判。

## 2.12 Harness 运行时（8 元件）

**查什么**：围绕模型的运行时壳是否齐备。**行业口径（至少 6 种）不统一，本规范采用地图口径（Harness=运行时八元件），引用外部分类只作对照不作主尺**。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.12.1 | 编排循环（Run loop） | 有 Orchestration/Run loop 元件：谁开始、谁停止、循环到完成或上限 | 无主循环概念，各自调用散落 |
| 2.12.2 | 工具边界（Tool boundary） | 工具调用经统一边界拦截/校验/记录，非模型直连任意函数 | 模型能绕过边界直接调底层 |
| 2.12.3 | 上下文检查点（Context/State/Checkpoint） | 运行中保存可恢复状态/上下文检查点 | 无检查点，中断全丢 |
| 2.12.4 | 重试/恢复与幂等（Retry/Recovery/Idempotency） | 重试策略明确；写类操作幂等保护；失败有恢复路径而非只能重跑 | 重试可造成重复副作用；失败只能从头重跑无恢复 |
| 2.12.5 | 护栏与人工介入（Guardrails/HITL） | 违规可拦截；关键点可人工介入/中止；安全策略在 harness 层执行 | 无拦截层，AI 输出直通执行 |
| 2.12.6 | 可观测性（Telemetry/Observability） | 运行全程有 trace/log/metric：每次调用、每步决策、耗时成本可看 | 黑盒运行，出问题无从查 |
| 2.12.7 | 评估挂钩（Eval harness hook） | 运行时能对接评估（跑样例/回归用例）；评估集运行不被 harness 干扰 | 无法在本体上跑评估；或评估与运行环境割裂 |
| 2.12.8 | 成本与延迟控制（Cost/Latency） | 每次调用成本/延迟可度量；有预算闸与超限降级 | 成本延迟不可知、失控 |

**检测注意事项（2.12）**：
- 八元件是**组合判据**：可对照八元件公开定义（awesome-agentic-ai-zh 课程 2-2 节，GitHub 可检索）逐项核对，缺哪件记哪件——缺件不直接判死，按 1 档位决定"缺件是否致命"（G1 工具可缺 HITL，G4 自主体缺 HITL 即阻塞）。
- "Agent = Model + Harness"：判断本体是否完整时，先识别"哪层是模型、哪层是 harness 壳"，别把模型能力当 harness 能力、也别把 harness 缺件算到模型头上。
- 六层评估框架（指令/上下文/工具/边界/反馈/治理）与 11 组件（LangChain）均只作旁证，不替代八元件主尺；若采用其中一种作为项目文档口径，只要求"能指出对应到八元件的映射"。

## 2.13 多 Agent 协作（Multi-Agent）

**查什么**：多 Agent 编排的协作质量：分工、通信、状态共享、冲突解决、效率开销、失败隔离、群体记忆。**默认不要用多 Agent**（1 四问已排除才单主体），用了才查本节的"协作不打架"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 2.13.1 | 角色分工清晰 | 每个 Agent 角色/职责/权限明确且互斥；角色数量有理由（不盲目堆砌） | 多 Agent 无明确分工，各角色职责重叠打架 |
| 2.13.2 | 通信与交接协议 | Agent 间消息/交接格式有协议；共享上下文有明确写入边界 | 通信无格式，A 的结果 B 看不懂 |
| 2.13.3 | 冲突解决机制 | 意见冲突有裁决机制（明确仲裁者/规则，非两 Agent 死循环互驳） | 多 Agent 观点冲突无人裁决、循环争论 |
| 2.13.4 | 开销与效率把关 | 引入多 Agent 的 token/延迟/复杂度开销有评估；不因堆 Agent 而低效 | 为演示堆多个 Agent，实际又慢又贵 |
| 2.13.5 | 失败隔离与恢复 | 某 Agent 失败不影响全局（降级/单点失败有隔离）；子任务失败可重试 | 一个子 Agent 崩整个编排全崩 |
| 2.13.6 | 群体记忆与一致性 | 多 Agent 共享状态/记忆有唯一权威源，不各记各的导致冲突 | 各 Agent 各写各的记忆，互相矛盾 |

**检测注意事项（2.13）**：
- **引用级反模式**：2.13.1 分工不清 + 2.13.3 无仲裁 = 最常见的多 Agent 失败（子 Agent 互相覆盖/争论/任务漂移）。检出这两点即 警示。
- 多 Agent 深度测评走乙类基准，本章只查"协作机制存在且不打架"。可用外部尺：
  - **MultiAgentBench**（Zhu 等，**arXiv:2503.01935，ACL 2025**）：以 **milestone-based KPI** 同时衡量**任务完成**与**协作/竞争质量**；并系统对比 **star / chain / tree / graph 四种协调拓扑**，以及 **group discussion（小组讨论）、cognitive planning（认知规划）** 两类策略。可直接借用的原文结论：**gpt-4o-mini 平均任务分最高、graph 拓扑在研究场景表现最佳、cognitive planning 使 milestone 达成率提升 3%**——可作为 2.13.1 角色分工与 2.13.2 通信协议的拓扑选型佐证（对应 MARBLE 开源框架）。
  - **ChatEval**（**arXiv:2308.07201**）：多 Agent 辩论式评审团，用于"判分器"侧（见 4 章）。
  - **SOTOPIA**（Zhou 等，**arXiv:2310.11667，ICLR 2024**）：社会智能与交互评估。
  - **引用纪律（易错点）**：MultiAgentBench **没有**官方的"协作效率 / 通信质量 / 冲突解决 / 资源分配"四维说法（该四词系二手转述，与原文摘要不符）。**写作与出报告时改用上列原文口径**；若只需一句，直接引"milestone-based KPI + 四种协调拓扑对比"即可。
- 与 2.12.1 编排循环的关系：多 Agent = 主 harness 循环内再套子循环；查 2.13 前先确认主 harness 八元件在（2.12），否则先补主循环再看协作。

## 本章收口：本体构成判定与后续分诊

2 跑完，输出**本体构成判定表**，字段如下：

1. **逐节结论**：2.1-2.13 每节 = 达标（齐）/ 警示（缺件待补）/ 不达标（严重缺失），附每节缺件清单。
2. **一票否决触发**：是否有 2.2.3（污染可重写系统指令）/ 2.3.3（无死循环防护）/ 2.10.2（写操作无幂等且会重试）等阻塞项——任一命中即不进入下一层，先整改。
3. **关键错位识别**：模型能力被误当 harness 能力、或 harness 缺件算到模型头上（2.12）——指出本体真实的薄弱层。
