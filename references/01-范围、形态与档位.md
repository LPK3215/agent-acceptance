# 1 范围、形态与档位

> **本章角色**：[全局地图 1](00-global-map.md) 的展开正文，整套规范的 **P0 必经入口 = 选层问卷**。任何一次检查都从这里开始。
> **一句话**：先证"确实需要 Agent"，再锁"长什么样 / 用什么 / 边界在哪 / 怎样算成功 / 自主到哪一档"——1 收口时输出一份**定档记录**，用它决定后续 2-10 哪些上场、按什么档位加码。
> **本章边界（防越界三句）**：（1） 1 只做**定档问卷**（要不要 Agent / 形态 / 技术栈 / 边界 / 成功标准 / 自主档），不提前执行 2-10 的任何判据，也不做量化打分——"做得好不好"归 3-5，"能不能放出去"归 7-9；（2） 模型本事、组织级认证、通用公平性等本规范不接的对象在 1.1/1.6 划界即剔除（详附录 A.1），不变成后续层反复纠缠的悬案；（3） 1 的 G1-G4 是**入口自主度档**，只决定后续加码强度，不承担 10 的出口结论档——两者不可互换。
> **被检方提供物（P0 门槛）**：形态 / 技术栈 / 目标边界 / 成功标准 / 自主度——口答或文档即可，不要求先有源码与评测资产。
> **使用方式**：逐条过检查点——（1） 达标/不达标/警示 标记 （2） 写证据（引文/文档/代码入口） （3） 不达标/警示 落整改建议。本章只做定性判点，不做量化打分。
> **依据原则**：正文判据自含、可直接执行；引用外部实证与口径处均已写实并按名可联网检索复核，不依赖任何本地文件取信息。

## 1.1 是否真需要 Agent（过度设计四问）

**查什么**：要做的任务是否真的只能由"多步推理 + 按上下文选工具 + 跨系统行动"的 Agent 完成；规则/结构化抽取/搜索/普通 RAG 够用时上 Agent 只是过度设计、徒增风险成本。

**判据（四问逐条过，任一不过 到 亮黄灯，记录"过度设计，建议降级"）**：

| 检查点 | 四问 | 达标信号（需要 Agent） | 不达标信号（应降级 / 拒绝立项） |
|---|---|---|---|
| 1.1.1 | （1） 是否必须跨多步完成？ | 目标天然依赖多步执行链（计划到执行到验证到修正） | 一次问答 / 一次检索 / 一条规则即可 |
| 1.1.2 | （2） 是否需按上下文选工具？ | 不同输入要动态挑不同工具/API，无法在代码里写死分支 | 工具路径固定，无"选择"动作 |
| 1.1.3 | （3） 错误操作是否可恢复？ | 出错会被权限/沙箱/回滚兜住，损失可控 | 一步错即不可逆（发钱/删数据/外发），且无人工闸 |
| 1.1.4 | （4） 新增成本风险有无业务价值支撑？ | 增量 token 成本 + 工具风险换来明确业务收益，有人算过账 | "别人都上 Agent"式立项，无 ROI 论证 |

**检测注意事项（1.1）**：
- 四问是"资格门"不是"装饰问"：四条全过才进入后续 1.2+；记录格式=每问一句项目原始表述 + 检查员判定，不写空话。
- 若判"不需要 Agent"，正确收口 = 记录"建议走规则/RAG/Workflow，属可迁移替代方案"，**不强行继续全流程验收**，可提示升级路径。
- 边界辨析：Agent 管非结构化判断/复杂分析，Workflow 管确定性规则流程（区别已在 1.1.1-1.1.3 的"信号"中体现：要动态选工具/要修正反馈才需要 Agent）；"多 Agent"默认不用，角色真需分工才加。
  - **外部口径佐证（可直接引）**：Anthropic《Building Effective Agents》（2024-12-19，[anthropic.com/engineering/building-effective-agents](https://www.anthropic.com/engineering/building-effective-agents)）给出的判别式与本节四问同向——**Workflow** = "LLMs and tools are orchestrated through **predefined code paths**（按预先写死的代码路径编排）"；**Agent** = "LLMs **dynamically direct their own processes and tool usage**，maintaining control over how they accomplish tasks（由模型在运行时动态决定自己的流程与用什么工具）"。
  - **落到判据**：**任务路径能在代码里穷举分支，则该走 Workflow，1.1 判"过度设计"；必须由模型在运行时动态选工具、动态定路线，才轮到 Agent**。检查时让被检方画出任务路径图，若分支可穷举即亮黄灯，此判据可直接写进 1.1 的证据记录。

## 1.2 载体形态

**查什么**：先定形态再定技术——**形态 不等于 技术栈**。形态决定技术选型与本套规范后续启用哪些检查面。

**形态六分法（命中的记下，可多选复合）**：Web 前后端分离 / 纯后端服务与 API / CLI / 桌面、IDE 插件 / 嵌入宿主应用 / 批处理无交互。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 1.2.1 | 形态归属与运行入口 | 能说出"我属于 X 形态 + 入口在哪"（URL / API 端点 / CLI 命令 / 宿主钩子） | 用技术栈冒充形态（"我们是 Next.js"）或答不出"长成什么样" |
| 1.2.2 | 形态 到 检查面启停映射 | 按地图规则启用对应面：含前端到交互呈现与 UX；纯后端到并发、鉴权、接口契约；CLI到参数、退出码、TTY；无 UI 形态到显式跳过前端面并记录 | 形态与后续启停不一致（无 UI 却硬查前端、有前端却漏 UX） |
| 1.2.3 | 宿主嵌入与集成出口 | 嵌入形态有真实宿主消费：能力以门户 / 业务系统 / 移动端 / WebApp / API 中至少一种出口被既有应用或用户使用；SSO 与权限继承已接入宿主（不另造一套账号体系） | 无任何集成出口，需用户切换到另一个孤立系统使用（自建门户把用户从原系统拉走） |

**检测注意事项（1.2）**：
- 形态复合时（如 Web + 批处理双入口）**各形态对应的检查面都要开**，不能只按主入口算。
- 纯后端/批处理若对第三方暴露 API：并发、鉴权、接口契约是必查面，与"有没有 UI"无关。
- 1.2.3 与"形态归属"（1.2.1）不同：1.2.1 问"Agent 自己长什么样、入口在哪"，1.2.3 问"能力有没有以嵌入方式被既有系统消费"（**"能集成发布"这一能力面的落点**，原文口径为"嵌入门户 / 业务系统 / 移动端 / WebApp / API"）。集成后的权限继承深检归 7.1 到 7.2；嵌入出口随宿主发版的版本化归 8.4。

## 1.3 技术栈

**查什么**：形态定后才有技术选择——语言 / 框架 / 运行时 / 编排与多 Agent 形态 / 依赖的 LLM 与工具平台。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 1.3.1 | 技术栈清单可陈述 | 能逐项列出：语言/框架/运行时/模型供应商与版本/工具平台，并解释"为什么这么选" | 只报品牌大词（"用了大模型"）无具体栈 |
| 1.3.2 | 五控制面视角对齐 | 能回答五问：Prompt 说清没 / Context 放够资料没 / Harness 能否安全用工具出错停 / Loop 怎么"做看再做"又不无限跑 / Graph 步骤分支能否看见并控制 | 除"调用模型"外无法说明任何一层 |

**检测注意事项（1.3）**：
- **技术只改判据"怎么写"，不改"查什么"**：本规范断言行为、不锁实现；语言/框架特有落点只作附注（如 TS/Node 与 Python 生态差异），不得以"XX 框架就长这样"跳过硬判据。
- 反模式提醒：模型升级（Model-Harness Fit）不等于 可拆护栏——移除某条补丁要拿同组 Eval 证明，权限/安全/log/eval/recovery 不因模型变强自动过时。

## 1.4 目标与任务边界

**查什么**：做什么 / 不做什么 / 交付物 / 拒绝场景——上线前边界先行，无边界最容易失控。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 1.4.1 | 用户与服务对象 | 能说清"给谁用、在什么环境跑" | 答"所有人/通用"说不清场景 |
| 1.4.2 | 任务输入与输出交付物 | 输入范围、输出交付物（报告/写库/消息/文件）有明确定义 | 输入无限、输出形态含糊 |
| 1.4.3 | 允许执行任务清单 | 列出"允许做"清单 + **最长运行时间上限** | "能做的事"无限扩张无清单 |
| 1.4.4 | 必须拒绝 / 转人工场景 | 明确哪些输入拒绝、哪些转人工；有替代方案，不做超权限承诺 | 未定义拒绝集，什么都接 |
| 1.4.5 | 交付物与"绝对禁止"书面化 | 按三类书面分：全自动 / 半自动需人工确认 / **绝对不允许 Agent 触碰** | 无风险边界书面记录 |

**检测注意事项（1.4）**：
- 与 1.1 是两回事：1.1 判"要不要做成 Agent"，1.4 判"做成之后圈多大地"——不可混。
- "无边界 = 未完成设计"：允许清单/拒绝清单/最长运行时间任一缺 到 1.4 判 警示/不达标，并直接影响 7 安全底线与 8 生产就绪的对应检查点是否可查。
- 最长运行时间可参考"任务超时即止"口径；具体数值在 8 生产就绪结合场景定，本章只记"有没有"。
- 目标清晰度四要素的落点：**用户（1.4.1）/ 任务边界（1.4.2-1.4.4）/ 成功指标（1.5.1）/ 非目标（1.5.2）**——检查时确认四要素不是靠"产品 sense"，而是有书面落点。

## 1.5 成功标准与验收口径（可测试）

**查什么**：成功标准必须可测试、可核验，不能是"效果不错"这种不可判口号。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 1.5.1 | 成功标准可测试 | 成功指标写成"在 X 输入下应产出 Y、且在 Z 情况拒答/转人工"式可核验句 | "回答得好/更智能/基本满足"不可测表述 |
| 1.5.2 | 非目标（Non-goal）明确 | 明确"本 Agent 不负责什么"，与 1.4 拒绝场景互洽 | 只写目标不写非目标 |
| 1.5.3 | 验收口径与后续章衔接 | 指出本项目的"任务成功"由哪层判（3 考卷 / 5 指标），能说清判分对象 | 验收口径悬空，没人知道怎么算"成了" |

**检测注意事项（1.5）**：
- 本节只锁"口径可测试"，**不锁具体阈值**（阈值落在 5 指标与目标值，且须由项目场景自推导，不可照抄行业参考线）。
- 验收时机前置提醒：验收标准应在启动时写成 CheckList 反向约束开发边界，而非上线前补——检查时看"验收口径是先于开发的约束还是事后的解释"。

## 1.6 自主度 / 角色分级与适用档位

**查什么**：项目实际自主到哪一档——越接近决策端，验收越严（全维评估 + 强监督 + 分级审批 + 可关停，高档位强制加码）。

**G 档分级（判断归档；监督侧取外部四级"工具到助手到协作者到自主体"作为档位直觉，正文按地图 G1-G4 落）**：

| 档 | 名称 | 特征 | 达标归档证据 | 不达标归档证据 |
|---|---|---|---|---|
| G1 | 工具层 | 只执行指令、不参与判断 | 人的指令决定一切，Agent 只跑确定性动作 | 实际会自行判断却报 G1（逃避验收） |
| G2 | 助手层 | 给建议、人拍板 | 输出建议/方案/预警，人保留全部决策权 | 建议之外还会自动执行关键动作 |
| G3 | 协作者层 | 与人对等分工，人在关键节点确认 | 承担完整任务，但关键节点有人工确认 | 关键节点无闸，实际全自动 |
| G4 | 自主体 | 全自主执行，闭环内独立决策 | 授权范围内独立决策执行 | 自称全自主却无监督/回退机制 |

**越自主越严的加码条款（按档位强制叠加，不可降档豁免）**：

| 检查点 | 加码项 | G1 | G2 | G3 | G4 |
|---|---|---|---|---|---|
| 1.6.1 | 验收侧重逐级变严 | 调用正确性/参数合规 | +建议质量/可解释性 | +边界内自主/关键点人控 | 全维评估 |
| 1.6.2 | 监督机制逐级前移 | 全量人工复核 | AI 只建议、人负全责 | 人工抽检 | 分级审批+自动回退通知人工 |
| 1.6.3 | 高风险动作审批门 | - | - | 关键点确认（强制） | **审批门强制** |
| 1.6.4 | 可回滚 | - | - | 警示 建议（写操作相关） | **强制** |
| 1.6.5 | 沙箱隔离 | - | - | 警示 视风险 | **强制** |
| 1.6.6 | 全链路 trace 回放 + 紧急关停 | - | - | - | **强制**（trace 回放 + kill switch + 完整审计） |

> **加码方向佐证**：外部学术尺 = **K. J. Kevin Feng、David W. McDonald、Amy X. Zhang《Levels of Autonomy for AI Agents》，arXiv:2506.12469（v1 2025-06 / v2 2025-07），华盛顿大学 Allen School，Knight First Amendment Institute"AI and Democratic Freedoms"系列出版**。该文按**用户所扮角色**定义五级自主度——**L1 operator（操作者）/ L2 collaborator（协作者）/ L3 consultant（顾问）/ L4 approver（审批者）/ L5 observer（观察者）**——核心论点为**自主性是独立于"能力"与"运行环境"的设计决策**，且该文正是**"自主性证书（autonomy certificate）"**概念的提出者（对应 1.6 注意事项的交付证据）。其"越自主越加码"序列与本表同向：L1-L2 只验结果质量 到 L3 加验规划/委派合理性 到 L4 强制审批门+可回滚+沙箱 到 L5 强制全链路 trace 回放+紧急关停+完整审计。
> 两把尺**方向一致、颗粒度不同**：**G 轴量"Agent 承担多少判断"，L 轴量"用户退到哪一步"**。本表按地图 G1-G4 落格；**L 级不逐格硬映射到 G 档**（L2 collaborator 与 G3 协作者层字面相近但定义不同轴；L3 consultant 在 G2/G3 之间无一对一落点），只用于佐证"G3/G4 必须加码的方向正确"。

**升降级判据（防止虚报档位）**：
- 升级前置判据："任何环节想升一级，先看该环节有没有可量化的验收标准"。
- 降级判据：观测指标**连续两个周期**明显恶化 到 降回上一级重新评估。
- 永不放权三类决策：**需求裁定、资源分配、风险容忍**——归到 G4 也不代表可交给 Agent。（*本条是**本规范自身的加严立场**，非外部尺原文：Feng 等的 L5 observer 允许用户退到"仅观察"，未设此例外；本规范要求此三类决策无论档位均须留人，且须在 1.4 书面边界里写明。写检查结论时按"本规范立场"引用，**不要写成"某论文要求"**。*）

**检测注意事项（1.6）**：
- 本套规范不锁单一自主度轴：业内并存两把尺——**角色参与度轴**（G1 工具层 到 G4 自主体，量"Agent 承担多少判断"，**本规范正文所用**）与**用户角色轴**（L1 operator 到 L5 observer，Feng/McDonald/Zhang，arXiv:2506.12469，量"用户退到哪一步"）。**方向一致、颗粒度不同**。本规范正文按地图 G1-G4 落；引用外部分级只作对照注，不作硬转换。
- **G 档低 不等于 风险低（分级轴独立，防"低档免责"）**：自主度只是验收尺之一——**监管影响分级 / 高风险应用清单是独立轴**：低自主工具若命中高风险应用清单，仍须按 9.5 强合规触发全维合规，不得拿"自主度 G1"挡合规。团队成熟度类组织级尺（T/CIIA 070 一档 L1-L5 评估模型）归组织治理、划出范围（附录 A.1.4）。**定档期须四问并答**：自主度几档（本表 G1-G4）？监管影响几级？是否命中高风险应用清单？组织级尺归谁评？
- **伪人审红线**：高自主项目必须证明监督"有意义"——检查抽检率/推翻率/告警响应时延，识别"有确认按钮但人根本不看"的橡皮图章式 HITL。
- **自主性证书（autonomy certificate）**为高自主档可交付证据：声明"我在哪一档、该档允许哪些动作/禁止哪些、越界如何兜底"——1.6 收口时建议直接要求 G3/G4 项目出此证书，与 1.4 风险边界书面化对齐。

## 本章收口：定档记录（输出件）

1 跑完，输出一份**定档记录**（模板字段如下），作为 2-10 的入场券：

1. **是否真需 Agent**：四问结论（通过 / 过度设计到降级建议）。
2. **载体形态**：六分法命中项 + 运行入口 + 启停检查面清单。
3. **技术栈**：语言/框架/运行时/模型与版本/工具平台。
4. **目标与任务边界**：用户 / 允许清单 / 拒绝与转人工清单 / 交付物 / 最长运行时间（有/无）。
