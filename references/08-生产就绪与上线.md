> **本章角色**：[全局地图 8](00-global-map.md) 的展开正文。**P3 运行与交付证据层第三节 = 生产就绪与上线**——6 让过程可见、7 让过程可信之后，8 回答"**能不能放出去、放了怎么收回来**"。本体（2）给能力、评测（3-5）给线、观测（6）给数据、安全（7）给底线，8 把这些组装成**一条能执行的上线流程**：四可核验 到 12 Gate 到 失败恢复 到 灰度回滚 到 go/no-go 到 事件响应 到 持续评估。

## 8.1 生产就绪四可（可观察、可评估、可调查、可验证）

**查什么**：生产就绪的**中心命题 = "评测通过 不等于 生产就绪"**——评测证明已知条件下表现，生产考验变化环境中的稳定性。四可 = 四条验收提问，一可（能埋点）做了不代表三可（能追版本+后果）做了。判四可逐条，而不是"有监控就算"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.1.1 | 真实运行中可观察 | 上线后 AI 运行现场**能被还原**：有 trace/run ID 贯穿、关键动作可重放 | 只有零散请求日志，还原不了任何一次完整运行 |
| 8.1.2 | 变化环境中可评估 | 能识别**线上任务与评测任务的差异**；质量下降能被发现（不只是服务不挂） | 只监控"接口通不通"，质量退化看不见 |
| 8.1.3 | 出现差异后可调查 | 低质量行为能追到**任务/版本/工具/知识/业务后果**，并解释差异如何形成 | 只发现"这轮不行"，说不清是哪一层变了导致的 |
| 8.1.4 | 改进后可验证 | 修复后能**重测确认真的改好**（同批样本/回归重跑），改动能看出前后对比 | 改了无法重测，只能"再观察看看" |
| 8.1.5 | 三链框架防"有 trace=有评估" | 分得清三层：**行为链**（发生了什么）/ **证据链**（为什么这样判断）/ **质量评估**（这次做得好不好）——埋点齐备 不等于 已有质量判断 | 把"有 trace"当"有评估"，从未对质量下判断 |

**检测注意事项（8.1）**：
- 只看第一可（埋点）不做第三可（追版本+后果）= 判不完整——评测发现差异、运行现场解释差异，两者必须能对上。
- **四可的出处与原文表述（引用纪律）**：四可出自**听云《AI 观测站》第 13351 篇（作者金全，2026-07-24）《Agent 评测都通过了，为什么还是进不了生产？》**。原文四件为："**在真实运行中仍然可观察**/**在变化环境中仍然可评估**/**在出现质量差异以后仍然可调查**/**在完成改进以后仍然可验证**"。
  - **以一手原文为准（易错点）**：第四可原文作"**可验证**"。公开转述中另有"可复验证"的写法，**引用一律以听云原文的"可验证"为准**，并连同"在完成改进以后仍然可验证"的完整原句一起引。
  - **判法不因用词改变**：无论写作"可验证"还是"可复验证"，8.1.4 的取证口径都是"**修复后能否重跑同批样本并复现结论**"（须有重跑记录与前后对比），不是"有没有做过一次验证"。
  - **可直接引的两句原话**："**评测通过，不等于生产就绪。评测证明的是已知条件下的表现，生产考验的是变化环境中的稳定性。**"；"**评测发现差异，AI 运行现场解释差异。**"
  - **与"三链"同源**：同系列第 13344 篇给出三链——**行为链**（发生了什么）/**证据链**（为什么这样判断）/**质量评估**（这次做得好不好），并警告"**Agent Trace 很完整，不等于企业已经知道一次 AI 行为做得好不好**"（8.1.5 的出处）。
  - **证据链核验六条件（完整版，补 8.1 简版）**：（1）**来源**（业务系统/知识库/工具真实返回/模型自生成，四者须区分）（2）**时间与版本** （3）**适用范围** （4）**是否被实际采用**——注意四层差异：**检索到 不等于 采用 不等于 形成充分依据 不等于 判断正确** （5）**支持与反对**（须保留反向证据，不能只留支持面）（6）**缺失与验证**（哪些关键事实没进现场）。核心原则："**不要把模型的自我解释直接当证据**"。
  - **质量评估（供 8.1.5 深化）**：= **四维判断**（结果质量/行为质量/边界质量/业务质量）**x** **六信号组合**（规则/参考结果/编译测试/业务系统核验/人工复核/LLM-as-a-Judge）。
  - **Oracle 七对象（供 8.7 持续评估）**：原文"evaluate the **answer, path, tools, state change, reliability, production behavior, and recovery** together"——即**答案/路径/工具/状态变更/可靠性/生产行为/恢复**七者**须一起评**；其中"**state change（状态变更）**"要求把 Agent 写库/发信/下单等**副作用独立成项**，只看"答案对不对"会漏。
- 证据链核验注意六条（简版）：来源（业务系统/知识库/工具真返/模型自生成）、时间与版本、适用范围、**是否真被采用**（检索到不等于采用不等于充分依据不等于判断正确）、支持与反对证据、缺失与验证；不要把模型的自我解释直接当证据。
- 与 6 分工：6 判"记录得全不全（trace 字段/回放）"，本章判"**四可流程**有没有跑起来（能识别差异到能调查到能验证）"。

## 8.2 上线前检查（12 Gate 主干）

**查什么**：上线前用**一道 launch gate** 而非一次人工演示定生死。12 Gate = G0 任务适配与边界 到 G1 权限与工具 到 G2 数据治理与记忆 到 G3 安全纵深 到 G4 人工确认 到 G5 评测门槛 到 G6 成本与性能 到 G7 可观测留痕 到 G8 失败隔离恢复 到 G9 发布回滚治理 到 G10 负责人与事件响应 到 G11 交付记录与文档。判"12 道 Gate 主干齐不齐、每道有硬判据、不重复 7/5 内容"。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.2.1 | Gate 主干齐备 | 有**成文的 Gate 清单**覆盖 G0-G11 各域，每道 Gate 注明通过条件与证据 | 只有口头"上线评审会"，无成文清单 |
| 8.2.2 | G0 适配与边界先行 | 先答**是否真需要 Agent**（规则/结构化抽取/普通 RAG 够用就不上 Agent）；允许执行任务/最长运行时间/必须拒绝场景/转人工场景/可测试成功标准**上线前已书面** | 无边界直接放；把不需要 Agent 的场景硬套 Agent |
| 8.2.3 | G1-G4 消费 7 结果 | 权限/工具/数据/护栏/HITL 的 Gate 检查项**引用 7 判定结论**（权限收敛、人工确认点等），不重复独立判一遍 | Gate 清单与 7 判定脱节，安全面被当"另行处理" |
| 8.2.4 | G5 Eval Gate 位置明确 | **Eval Gate 挂在发布流程里**（通过才进下一环节）；发布对象各版本（模型/Prompt/RAG index/tool schema/MCP/策略）变更都触发重过 | Eval 与发布流程无关，改完直接发 |
| 8.2.5 | G6 成本性能预算门 | 上线前设**单任务成本估算与上限、每日上限/频率限制/预算告警、性能目标（首字/完整响应/P99）**（参考口径） | 上线前不估成本/性能，等费用异常或超时再补 |
| 8.2.6 | G7 观测留痕门 | 每会话记录链路字段（trace_id/输入/检索/工具/输出/风险级/人工确认/最终动作）；日志可回放、可导出 | 只记请求响应，不记中间链路（无法回答"谁确认了什么"） |
| 8.2.7 | G11 交付记录与文档 | 上线前备齐交付记录：Agent 目标/工具清单/权限等级/人工确认点/知识库来源/成本限制/日志位置/回退方案 | 无记录，后续维护/出险无人能接手 |

**检测注意事项（8.2）**：
- 12 Gate 的分域深层判据**不在此处重复**：G1/G3/G4 深层归 7，G5 深层归 3/5，G7 深层归 6，G8/G9/G10 在本章 8.3-8.6 展开——8.2 只判"主干齐不齐、每道 Gate 有没有成文通过条件"。
- 上线前清单参考口径：最小上线 7 条 / 上线前 13 项 / 治理 30 问 / 八阶段 40+ 项（公开清单，按项目档位裁剪使用，逐条勾选要有证据而非口头）。
- 若被检方只有"无测试团队/无清单"的解释，可参考公开替代路径（真实用户对话数据做测试集 / 非开发同事小白测试 / AI 生成边缘用例 / 小范围灰度真流量验证）——但替代路径也须进 Gate 记录。

## 8.3 失败隔离与恢复（沙箱 / checkpoint / 幂等 / 回滚 / 急停）

**查什么**：生产就绪不是保证不出错，而是**把错误限制在可控范围内**。判五件：高危执行在笼子里（沙箱）、写前可存档（checkpoint）、重试不重复（幂等）、出险能收（回滚预置）、紧急能停（急停开关）。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.3.1 | 沙箱隔离声明与后端匹配 | 高风险执行进**沙箱**；隔离强度与部署后端绑定（local/Docker/K8s/Worker），声明里写清"隔离到什么级别" | 把"用了沙箱"当固定隔离保证；高危调用直连宿主/生产 |
| 8.3.2 | 写前 checkpoint + 持久化 | 写操作前保存 **checkpoint**；长任务 checkpoint 可恢复；production 用**持久化 state 存储**（durable checkpointer）而非仅内存态 | 无 checkpoint，中断即丢任务/无法续跑 |
| 8.3.3 | 幂等设计 | 写操作有 **idempotency key**：重试/超时重放不会重复发邮件/付款/写数据 | 重试即重复副作用（重复下单/重复外发） |
| 8.3.4 | 回退方案预置 | 上线前备好回退五件：**禁用工具 / 切模型 / 暂停 Agent / 恢复旧版本 / 转人工**；每件有触发条件 | 出险无回退预案，只能现想 |
| 8.3.5 | 急停开关（fail closed） | 有**急停开关**：≤60s 内禁用 Agent、**禁用时 fail closed（不做任何操作）**、定期测试（参考口径：每月） | 无急停；急停后 Agent 仍继续动作 |
| 8.3.6 | 故障演练与 Runbook | 有故障演练记录 + Runbook（出事照着做的步骤），不靠开发者临时排查 | 无演练无 Runbook，只能靠发明者现场救火 |

**检测注意事项（8.3）**：
- 与 7 分工：权限面（危险操作闸门/沙箱的准入与审批）归 7.2/7.4；本章判**运行侧恢复机制**——checkpoint/幂等/回滚/急停这些"出事后怎么收"的工程件。
- 事件/事故处理全流程参考 **NIST SP 800-61 Rev.3**（准备到检测到响应到改进）的口径组织。
  - **出处精确信息（已回源）**：**NIST SP 800-61 Revision 3，《Incident Response Recommendations and Considerations for Cybersecurity Risk Management》，2025-04-03 定稿**，官方页 `csrc.nist.gov/pubs/sp/800/61/r3/final`。
  - **引用纪律**：Rev.3 的**标题已改**（不再是旧版的 "Computer Security Incident Handling Guide"），写报告时**用新标题 + Rev.3**，避免读者按旧标题检索不到。
- checkpoint 里的 state 可能含上下文与运行时元数据，须按敏感资料管理（与 7.6 数据治理联动）。

## 8.4 灰度与回滚治理（版本化发布对象）

**查什么**：发布对象**不只是代码**——Prompt/模型/RAG index/工具 schema/MCP Server/策略配置全是发布对象，要**版本化、可灰度、可回滚**。判三件加资源依赖一项：版本化覆盖全不全、灰度是否渐进逐级 gate、回滚预案是否真可执行、外部依赖资源（数据源/第三方 API/密钥与配置）是否显式声明并纳入版本化治理（8.4.6）。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.4.1 | 发布对象全版本化 | 发布对象清单含**代码 + Prompt/模型/RAG index/工具 schema/MCP/策略配置**，全部有版本记录可追踪 | 只版本化代码，Prompt/模型/策略改了无版本可回 |
| 8.4.2 | 灰度渐进 + 逐级 gate | 灰度按**逐级放量**推进（参考节奏 1%到5%到20%到50%到100%，每级观察核心指标合格才进下一级） | 一把全量上线；或灰度无逐级观察 |
| 8.4.3 | 回滚触发预案成文 | 回滚触发条件成文（参考口径：错误率>20% 自动回滚<1min / 投诉激增手动<5min / 安全事件紧急下线+回滚<2min，按场景校准） | 无触发条件，等出事再开会讨论 |
| 8.4.4 | 回滚可执行 | 回滚脚本**已测**、回滚后**数据兼容**、团队**熟悉流程**；变更记录可追踪 | 回滚方案停在纸面，没人跑过 |
| 8.4.5 | 放量策略含质量/安全/成本 | 放量 gate 不只看流量，含**质量指标/安全合规/成本预算**（进 canary 的条件成文） | 放量只看"服务没挂"，质量与成本不进 gate |
| 8.4.6 | 外部资源依赖治理 | 依赖清单可枚举（模型服务 / 数据库 / 第三方 API / 密钥与配置 / 文件存储）；依赖变更（schema 升级 / API 契约 / 配置）纳入版本化与回滚对象；依赖不可用可告警、有降级或恢复路径，不静默失败 | 依赖隐性散落无清单；外部依赖挂掉后静默失败 / 无限重试 / 无恢复路径 |

**检测注意事项（8.4）**：
- 8.4.6 是五能治理面之"资源依赖"一项的落点：与 8.7.3 环境漂移分工——8.4.6 管"依赖**声明与变更治理**（清单、版本化、回滚）"，8.7.3 管"依赖**运行中漂移/可用性监控**"；与 2.1.5 分工——2.1.5 只管模型调用成本与配额，不含第三方 API / DB 等外部资源。
- 5.4.7 判"CI 接入阶段规划**设没设**"；本章判"灰度**执行**——是否真逐级放、逐级看、超线回滚"。
- **A/B/灰度结论按分群拆解复核**：放量依据若来自对照实验，须按用户分群拆解后再下判断（总体显著可能掩盖"仅新用户提升、专业用户无变化甚至退化"），避免把子群失效当整体通过。
- 参考口径数字须按场景校准；灰度各阶段观察什么指标（成功率/延迟/成本/安全信号）要写死，不临时拍。

## 8.5 复认证触发与 go/no-go 决策

**查什么**：上线不是一次性的——**改了就重新确认**（recertification），不是"事故处理完就算修好"。go/no-go 不是人开会拍脑袋，而是**执行 5.4 的决策映射**，留下机器可消费的证据。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.5.1 | go/no-go 执行决策映射 | 每次发布按**成文决策映射**执行（任一 hard blocker 则 block；无 blocker 且总分 ≥90 则 continue；80-90 则 canary_only；<80 则 manual_review/block，阈值取 5.4 定义值） | 决策靠人临时拍；有映射不执行 |
| 8.5.2 | Scorecard 每发必出 | 每次发布产出**结构化评分卡**（release_id/environment/window/score/decision/hard_blockers/SLI 快照/evidence），机器可消费 | 评分卡自由文本/事后补写/只发布当天算一次 |
| 8.5.3 | 复认证触发条款 | 有**复认证触发清单**：事故 / 换模型 / 改提示词 / 加工具 / 季度到期（至少含这几类），触发即重过评估门禁 | 只上线前验一次，改完不重验 |
| 8.5.4 | 事故 到 复认证闭环 | 事故处理完**不算修好**：走复认证流程 + 复盘沉淀回归样本后才能再放量 | 事故修完直接恢复上线，不重过认证 |
| 8.5.5 | 评估数据来源合法 | 复认证/上线评估用的数据不是训练/开发数据（不与 3 污染判据冲突）；gold 集有 hold-out | 用开发数据当上线评估（自证清白不成立） |

**检测注意事项（8.5）**：
- 5.4 定义线与映射（目标线/评分卡契约字段）；8 判**执行**：有没有真跑、block 有没有真 block、复认证有没有触发条款。两者互补，勿重复判"契约定义"。
- 5 个决策问题贯穿评分：任务是否成功 / 失败是否可解释 / 风险是否可接受 / 观测证据是否完整 / 发布动作是什么——评分卡要能回答这 5 问。

## 8.6 事件响应与负责人制度（值班 / 升级路径 / 事故复盘）

**查什么**：生产 Agent 必须有**负责人与事件响应路径**——"没有负责人，Agent 出错时就会变成所有人都着急、没人能处理"。判四件：角色写清、升级路径、遏制与复盘、复盘产物回流。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.6.1 | 角色与职责写清 | 上线前写清：**谁看监控 / 谁处理报警 / 谁审高风险动作 / 谁维护知识库 / 谁决定暂停**（可一人多岗但必须可指认） | 无负责人，出事人人着急没人能处理 |
| 8.6.2 | 升级路径成文 | 有**升级路径**（参考：Agent 所有者到安全团队到CISO到管理层，重大事件到董事会级）+ 用户通知时限（如 GDPR 72h，强合规适用） | 无升级路径，重大事件不知该报谁 |
| 8.6.3 | 遏制手册 + 复盘制度 | 有**遏制手册**（数据泄露/失控行动/注入/滥用的处置步骤）；事件后限期复盘（参考：5 个工作日内无指责复盘） | 无手册无复盘，事件过了就过了 |
| 8.6.4 | 复盘产物回流 | 复盘结论**反馈回 Gate 清单与回归样本**（不是只写一篇总结） | 复盘止于会议/文档，清单与样本不更新 |
| 8.6.5 | 值班与响应时限 | 有值班安排与响应时限约定（P0/P1/P2 分级：电话+短信+群 / 短信+群 / 群，参考口径按场景校准） | 无值班无时限，报警没人响应 |

**检测注意事项（8.6）**：
- 与 7.5.4 联动：事故到回归用例的**安全侧**归 7.5，本章补**全事件响应流程**（值班/升级/复盘制度）。
- 复盘制度判"无指责 + 反馈回清单"，只复盘不回清单=复盘是空转。

## 8.7 生产持续评估与漂移监控（KL 偏移 / 趋势 / 回归节奏）

**查什么**：上线后评估不能停——Oracle 定位"Enterprise agent evaluation is not a one-time release activity"。判四件：持续算趋势、回归有节奏、漂移能发现（输入分布/环境/质量）、失败回流成闭环。

| 检查点 | 查什么 | 达标信号 | 不达标信号 |
|---|---|---|---|
| 8.7.1 | 持续评估非一次性 | 评分卡/质量评估**每日或按节奏持续计算**（观察错误预算消耗趋势），不是只在发布当天生成 | 发布当天算一次，之后再也不看 |
| 8.7.2 | 回归节奏明确 | 有**回归节奏**（参考口径：核心回归每次发布、回归集每周至少一次、安全/风险样本按 7.5 节奏）；上线后数据源/权限/工具/输入方式变化是复发主因，回归跟着变化触发 | 无节奏；上线后从未重跑过任何评估 |
| 8.7.3 | 漂移监控 | 能发现三类漂移：**输入分布漂移**（用户问法/任务构成变了）、**环境漂移**（数据源/知识库/依赖站点/工具权限变了）、**质量漂移**（指标/性能随时间退化）；分布偏移有监控信号（如 KL 偏移/指标趋势/异常检测） | 只盯错误率，输入构成与质量退化看不见 |
| 8.7.4 | 失败回流闭环 | 线上失败/灰度失败**沉淀回数据集**（去识别化），成为新回归样本（与 3.8.1 联动）；每周/每月新增失败案例分析 | 失败留在日志里，不进评估集不复用 |
| 8.7.5 | 模型/护栏变更监测 | 换模型/升级/拆护栏有**行为漂移复测**（Model-Harness Fit：模型变强不自动过时权限/安全/log/eval/recovery）；guardian 变更对照评估 | 模型升级后不重测，或顺手拆护栏无证据 |

**检测注意事项（8.7）**：
- 与 3.6/3.8 分工：3 判"回归层**有没有**、数据集回流机制**有没有**"；本章判"**生产侧持续跑**——节奏、趋势、漂移监控、变更复测是否真在执行"。与 4.5 judge 漂移监控（判分器自身的校准漂移）互补：8.7 管 Agent 行为/输入/环境漂移。
- "发布对象每次变更都重过评估"与 8.5 复认证同源：8.7 管**持续观测节奏**，8.5 管**事件驱动的重新认证**。
